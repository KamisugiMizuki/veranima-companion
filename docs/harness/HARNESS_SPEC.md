# 陪伴心智 Harness（HARNESS_SPEC）

状态：**提案，未动工**（09-06 用户裁决：先写 spec，之后做）。
一句话：把「角色内部状态」从散落在各模块的私有实现，收拢成统一操作的
对象层——记忆、睡眠、牵挂、动态、画像都是同一类东西：**带时间线的事实源，
经判断点决定是否产出对外行为，产出必须留痕**。

## 1. 动机（09-06 真机筛查实锤）

这批线上问题没有一个能靠单点修补根治，因为它们同属一个结构缺陷：

| 症状 | 结构病因 |
|---|---|
| 苏醒总结连播 4~6 次 | 去重键记在共享账表，多消费方各写各的、互相踩 |
| 「上次你说那事」逐字三连 | 降级模板无消费账，每次重启当第一次 |
| 「三个小时没动静」估时错 | 素材生成时刻与发送时刻脱节，出闸无人复核 |
| 判词「用户认真回应了直接问题」当记忆复述 | 写入无判断点把关，消费无类型过滤 |
| 「你们公司聚餐」凭空编造 | 产出前没有事实校验位可言——管线里没有这个环节 |

共同形状：**副作用（发消息/写记忆/落动态）绕过了统一的可否决闸**，
且决策过程不留痕——导致线上只能靠导出 DB 猜「它当时为什么这么做」。

## 2. 五段协议（对象生命周期）

每个「可 harness 操作的对象」= 走通这条管线的一次实例：

```
事实源(source) → 判断点(judge) → 待织池(pool) → 闸(gate) → 产出(effect)
                     ↑                                     ↓
                 决策留痕(decision log) ←←←←←←←←←←←←←←←←←←←
```

各段现状与差距（以真机已跑链路为准，不新建平行栈）：

- **事实源**：已有。sleep_cycles / mind_threads / memories / usermodel /
  virtual_life_events / proactive_feedback。要求=每源有稳定 id 与时间线。
- **判断点**：已有统一裁决（judges 每消息一次调用）。差距=多数副作用
  只过「能不能发」的资源闸（日上限/间隔/静默），不过「该不该发这条内容」。
  本 spec 的核心增量：**内容闸**——产出前对候选做最后一次可否决判断，
  输入含素材生成时刻与当前语境的偏差度。
- **待织池**：已有（tick_proactive 待织池 + 合并窗口）。差距=池的语义
  只在问候族实现，睡眠/动态/记忆写入各自攒各自发。
- **闸**：已有 ProactiveGate 九门。要求=所有出口（对话回复除外）一律过闸，
  旁路通道（bridge 通知补发）收编为池的普通消费者——09-06 的 claimed 列
  就是这个方向的第一块砖：认领状态长在对象行上而非账表。
- **决策留痕**：**没有，本 spec 的主新件**。新表 `decisions`。

## 3. decisions 表（唯一的新结构）

```
decisions(id, ts, kind, object_ref, candidate, verdict, reason,
          input_digest, effect_ref)
```

- `kind`：wakesummary / meal / thread_speak / moment_publish / memory_write /
  proactive_woven …（副作用类型，闭集，加类型=加一行常量）
- `object_ref`：被操作对象指针（`sleep_cycle:7`、`thread:12`、`memory:188`）
- `verdict`：sent / vetoed / expired / deduped / degraded
- `reason`：判断点/闸给出的短句（人读，导出即复盘）
- `input_digest`：决策时读到的关键输入摘要（≤200 字，防「导出猜不回」）
- `effect_ref`：产出去向（message id / 无）

成本：每次副作用一行 INSERT，SQLite 单机零压力。真到百万行再谈清理
（ponytail 同款：先跑起来，出现磁盘投诉再做滚动删除）。

## 4. 回放（harness 的真正收益）

导出物从「DB 快照」升级为「决策序列」：

- `decisions` 按时间排开=这个角色今天为什么说了每句话的完整账本；
- 复现线上问题从「导出→SQL 考古→猜」变成「导出→按 object_ref 过滤→看 reason」；
- 新判断点的验收=对同一批 decisions 重放裁决，比对 verdict 差异（回归测试
  的数据源不再是手写的 fixture 消息）。

## 5. 边界（不做什么）

- **不抽通用 agent 框架**：五段协议是本项目内部的具体表/具体函数，
  不做接口层、不做注册表、不接第三方实现。
- **R5/Hermes 执行后端不进本协议**：那是外派任务通道（异步终态+审批
  状态机），语义不同，硬收拢会把审批污染成判断点。
- **对话回复主链不强制走 decisions**：一问一答是同步行为，judges 已有
  裁决缓存；留痕只覆盖**自发副作用**。

## 6. 分期（动工时按此顺序，每步独立可回滚）

1. **D1 留痕先行（零行为改动）**：建 decisions 表 + 现有四类副作用
   （wakesummary/meal/thread/moment）发一条记一条。跑一周，肉眼对比
   导出——先证明「账本说得清为什么」，再动管线。
2. **D2 内容闸**：tick 出池前对每条候选加一次裁决（素材时效/语境复核/
   事实闭集校验——09-06 的 probe 保鲜闸与「公司」红线词是它的手写原型）；
   否决写 decisions 不发。判断点哲学不变：规则预筛、LLM 裁决、fail-open。
3. **D3 收编旁路**：bridge 通知补发、QQ adapter 独立路径全部改为池的
   消费者（认领列模式推广——09-06 sleep_cycles.claimed 是第一个样板）。
4. **D4 回放工具**：cli 加 `replay --from-export <dir>`：载入 decisions，
   重跑判断点，输出 verdict 差异表。设计验收（「她像不像人」）第一次
   拥有可回归的数据面。

D2/D3 完成后，M2 驱力池、M3 夜眠消化直接按本协议接线（它们的池/闸/留痕
全部现成），两件事合并推进——这也是先做本 spec 而非先做 M2 的理由。

## 7. 开放问题（动工前拍板）

- Q1 内容闸的 LLM 调用预算：每候选一次（≤128 token 小裁决）还是池合并后
  一次批量裁决？（倾向批量——与 _weave_ritual 同调用顺路）
- Q2 decisions 是否进备份包？（倾向进——单机量小，复盘价值大）
- Q3 对话主链的判断点（judges）要不要也落 decisions？（D4 回放若不含它，
  回归面缺一块；但它量大，每天数百条）
- Q4（09-06 用户提案）作息适应进 harness 参数面：现行结构=用户起床中位数
  vs 角色 wake_end、差值 1/4 渐进、卡 max_offset_minutes（bug 已修，但结构
  仍是单点锚+单向规则）。目标形态=以「作息重合度」为驱动的连续调参：
  取双方 wake/sleep 窗的交叠比例（近 3-7 周期 vs circadian 模板），重合度
  低=想陪却没窗口（值得动）、重合度中高=别折腾（阈值滞后防振荡——旧版
  recovery 每日回拉 10min 与适应 +120min 打架正是没做滞后的症状）。动多少/
  往哪动都成为 harness 上可读可调的参数，理由消息仍走待织池。归入 D2 同期。
