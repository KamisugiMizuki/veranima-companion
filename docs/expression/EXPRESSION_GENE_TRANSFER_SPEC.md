# 表达基因迁移系统设计契约

> 设计名称：表达基因迁移系统（Linguistic Gene Transfer System）
>
> 实现名称建议：用户表达特征学习（`ExpressionFeature Learning`）
>
> 状态：**明确暂缓实现**（当前不采集、不激活、不做模型微调）
>
> 版本：v0.1
>
> 日期：2026-08-23
>
> 适用项目：Veranima
>
> 本文是冻结的后续设计方案，不代表当前代码已经实现本功能。当前代码中已有的 `LanguageMirror`、`StyleLearner`、`UserStyleProfile`、`StyleBrief` 和 `ResponsePlan` 不等于本方案已经启用；它们只是未来实现时可能复用的入口。

## 1. 设计原点

用户与 AI 相处一段时间后，双方可能会自然借用对方的一些词语、句式和表达节奏。这种变化应当产生“熟悉感”，而不是产生机械模仿、人格同化或用户原文泄漏。

本系统的目标不是让 AI 复制用户，而是让角色在保持自身核心人格的前提下，逐渐理解并有限度地吸收少量用户表达特征：

```text
用户表达
  -> 观察候选
  -> 稳定性验证
  -> 角色与安全校验
  -> 低权重表达建议
  -> 主 LLM 自然生成
  -> 用户反馈修正或撤回
```

正确范式：

```text
用户：今天真是绝绝子。
AI：这个词你最近用了好几次。按你的语境，应该是在说今天心情不错？
```

而不是：

```text
AI：绝绝子！我今天也是绝绝子！
```

“表达基因”是产品侧的比喻。实现层不创建会改写人格的黑箱，也不修改模型权重；它只维护可解释、可回滚、低权重的表达特征。

## 2. 核心优先级

运行时优先级固定为：

```text
角色核心与安全边界
> 用户本轮明确要求
> 事实正确与语义完整
> 通道规则（IM/TTS）
> 当前关系、情绪和场景
> 已确认的用户表达特征
> 未确认的候选特征
```

表达特征永远不能：

- 覆盖角色卡的核心人格、价值排序、边界和能力范围；
- 把用户观点、经历或主题事实变成角色自己的观点或经历；
- 改写用户本轮的明确风格要求，例如“短一点”“详细解释”；
- 破坏事实回答、情绪接纳、冲突处理或现实行动边界；
- 绕过 `Reply` 解析、历史持久化和 IM/TTS 渲染出口；
- 影响思考过程清理、敏感信息清理或错误降级。

## 3. 与现有 Veranima 架构的关系

本系统不新增平行的“人格基因库服务”，而是挂载到现有学习和人格循环边界内。

| 设计模块 | Veranima 现有入口 | 设计处理 |
|---|---|---|
| 表达特征捕获 | `src/veranima/core/learning.py` | 扩展现有学习模块，所有输入来自 `user_text` |
| 用户整体文风统计 | `UserStyleProfile` / `StyleLearner` | 继续负责长度、正式度、直接度、标点和节奏等聚合值 |
| 低频词镜像 | `LanguageMirror` | 保留兼容接口，后续内部可演进为特征存储 facade |
| 人格候选校验 | `core/persona.py` | 只处理需要进入用户模型/交互规则的明确语义，不把普通口癖当世界观 |
| 表达提示 | `StyleBrief` / `ResponsePlan` | 统一生成短的低权重 prompt block |
| 长期事实和共同经历 | `MemoryStore` | 表达特征默认不进入 `memories` |
| 可见输出 | `Reply`、`render_im()`、TTS renderer | 只消费解析后的 `Reply`，不直接拼接用户原文 |
| 删除与重置 | 现有 style reset / corpus 生命周期 | 表达特征需要独立撤回、停用和全量重置语义 |

现有 `UserStyleProfile` 负责“用户通常怎么说”，例如平均长度、问句比例和正式度；本设计新增的 `ExpressionFeature` 负责“用户偶尔稳定使用了哪些具有语用功能的表达”。二者不能混成一套数据。

## 4. 范围与非目标

### 4.1 未来候选范围（暂缓）

第一阶段只处理：

- 用户重复使用的低风险词语或短语；
- 少量可抽象的句式结构；
- 经过场景和角色适配后可低频提示主 LLM 参考；
- candidate / observed / confirmed / rejected / expired 生命周期；
- 单轮最多一个表达特征；
- 使用冷却、频率上限、负反馈降级和用户撤回；
- IM/TTS 通道差异化约束。

### 4.2 明确不做

暂不实现：

- 模型微调、LoRA、在线 RLHF/PPO；
- 新的向量库、图数据库、独立记忆服务；
- 自动重写 Character Core；
- 自动把用户价值观写成角色信念；
- 无审核的全量聊天语料学习；
- 保存用户完整原句并在回复中复读；
- 复制口吃、重复字、语言障碍或明显个人缺陷；
- 把主题专名、项目名、游戏名直接当成表达基因；
- 用复杂的黑箱激活模型替代确定性门槛；
- 第一阶段的设置 UI；
- 第一阶段的深度“自然内化”模式。

## 5. 表达特征类型

### 5.1 `lexical_expression`：词语或短语

示例：

```text
草
绷不住了
这下坏了
又来了
```

保存的是表达本身和经过校验的语用提示，不保存用户完整上下文：

```json
{
  "kind": "lexical_expression",
  "surface": "绷不住了",
  "function": "无奈或好笑",
  "scopes": ["闲聊", "调试"]
}
```

### 5.2 `phrase_pattern`：抽象句式

示例：

```text
又{topic}是吧？
这也能{action}？
不是，你{claim}
```

只保存抽象结构和语用功能，不保存一整句用户原文：

```json
{
  "kind": "phrase_pattern",
  "pattern": "又{topic}是吧？",
  "function": "轻度调侃或确认",
  "scopes": ["闲聊", "轻度吐槽"]
}
```

### 5.3 `emotion_marker`：情绪标记

示例：

```text
？？？       可能表示惊讶或无语
……行吧     可能表示无奈或收束
哈哈哈      可能表示轻松或开心
```

情绪标记必须绑定语境，不允许全局机械复制问号、感叹号或重复字。

### 5.4 由 `UserStyleProfile` 负责的统计特征

以下不新建 ExpressionFeature，而继续使用现有聚合画像：

- 平均消息长度和平均句长；
- 短句/长句比例；
- 换行、括号、省略号、问号和感叹号比例；
- 正式度与直接度；
- 复杂问题的展开偏好；
- IM 与 TTS 的节奏差异。

## 6. 默认拒绝学习的内容

以下内容不进入表达特征候选，或直接标记为 `rejected`：

| 内容 | 处理原因 |
|---|---|
| 密码、token、验证码、支付信息、联系方式 | 安全边界 |
| 口吃、重复字、语言障碍 | 不应模仿用户缺陷 |
| 明显攻击性、歧视性、威胁性表达 | 可能造成关系越界 |
| 角色核心明显不适配的表达 | 保持角色一致性 |
| 只出现一次的流行语 | 可能是偶发或引用 |
| 主题专名、作品名、项目名 | 更可能是事实或兴趣，不是风格 |
| 代码、日志、URL、引用块、系统文本 | 不是自然表达样本 |
| 他人台词、文章片段、原作文本 | 授权和身份混入风险 |
| 用户完整句子 | 防止逐字复读 |
| 用户观点、经历、价值判断 | 应进入 User Model/Persona Loop，不是表达特征 |

## 7. 数据流与职责边界

### 7.1 固定流水线

```text
用户消息
  -> 记录原始 user message（现有 messages 表）
  -> 规则捕获表达候选
  -> 归一化、去重、敏感检查
  -> 更新短期候选状态
  -> 现有 Agent 生成 Reply
  -> 从 Reply/用户后续反馈提取可解释反馈
  -> 更新表达特征状态和使用记录
  -> 保存独立 style 状态
```

表达学习失败不能阻断正常回复。捕获器、标注器、保存器任何一步失败，都应让本轮对话继续使用角色默认风格。

### 7.2 数据来源铁律

只允许从用户侧输入捕获：

```text
允许：user_text
禁止：assistant text、system prompt、EvidencePack、搜索结果、工具 stdout、日志、TTS 文本
```

assistant 回复只进入正常聊天历史，不自动成为用户表达学习样本。

### 7.3 LLM 职责

LLM 只允许做有限候选标注，例如：

```json
{
  "kind": "lexical_expression",
  "function": "调侃或无奈",
  "scopes": ["闲聊"],
  "role_compatibility": "allowed",
  "confidence": 0.72
}
```

LLM 不得：

- 直接写入数据库；
- 生成 `feature_id`、版本号、删除动作或激活动作；
- 决定角色核心是否被修改；
- 输出可直接给用户看的表达学习内部对象。

程序必须对 LLM 候选重新做字段白名单、长度、敏感性、作用域和角色适配校验。标注失败时，候选最多保持 inactive，不影响对话。

## 8. 特征数据契约

第一版建议复用现有 `style.json`，不进入 `MemoryStore.memories`。可采用兼容扩展字段：

```json
{
  "schema_version": 4,
  "expression_features": {
    "candidates": [],
    "confirmed": [],
    "rejected": [],
    "version": 1
  }
}
```

单条特征的设计结构如下：

```json
{
  "feature_id": "expr_7f31",
  "kind": "lexical_expression",
  "surface": "绷不住了",
  "normalized": "绷不住了",
  "function": "无奈或好笑",
  "scopes": ["闲聊", "调试"],
  "first_seen_at": "2026-08-23T12:00:00+08:00",
  "last_seen_at": "2026-08-23T12:30:00+08:00",
  "occurrence_count": 4,
  "distinct_day_count": 2,
  "distinct_context_count": 2,
  "confidence": 0.64,
  "status": "candidate",
  "activation_level": "observe",
  "use_count": 0,
  "last_used_at": null,
  "source_message_ids": [101, 108, 113],
  "source_hashes": ["short-hash-1"],
  "role_compatibility": "unknown",
  "user_confirmed": false,
  "user_rejected": false,
  "expires_at": "2026-09-06T12:30:00+08:00"
}
```

约束：

- `surface` 和 `pattern` 只能是短表达，不能保存完整对话原文；
- `source_message_ids` 只用于审计和撤回，不直接注入 prompt；
- `source_hashes` 只保存短哈希或摘要标识，不保存可逆原文；
- `confidence`、次数和时间由程序维护；
- 任何特征必须支持停用、删除和重置；
- schema 迁移必须向后兼容旧 `style.json`，旧文件没有该字段时视为空集合。

## 9. 生命周期与晋升条件

### 9.1 状态

```text
observed
  -> candidate
  -> confirmed
  -> observe_only / rejected / expired
```

含义：

- `observed`：只在内存或短期状态中看到，暂不稳定保存；
- `candidate`：已达到最低出现次数，但尚未允许自然使用；
- `confirmed`：稳定性和角色适配通过，可低频注入 prompt；
- `observe_only`：可以理解或在必要时提及，但不主动使用；
- `rejected`：用户拒绝、角色不适配或安全检查失败；
- `expired`：长期未出现或未使用，自动失效。

### 9.2 默认门槛

纯实现参数由实现阶段根据行为测试最终固定；当前设计默认值如下：

```text
第一次出现：observed，不持久化或只保留短期计数
至少出现 3 次：candidate
跨至少 2 个自然日或 2 个不同场景：允许进入 confirmed 评估
角色适配通过且无负向反馈：confirmed
confirmed 后长期不再出现：先降级 observe_only，再过期
```

不采用“出现三次就直接使用”的规则。单一主题内复读、用户引用他人话或短时间连续重复，都不能证明是稳定表达习惯。

## 10. 角色适配与安全筛选

### 10.1 适配结果

每个候选必须得到以下之一：

```text
allowed       可以在合适语境低频使用
observe_only  可以理解或提及，但不主动使用
rejected      不进入激活池
```

角色适配检查只决定“能否作为表达方式使用”，不决定角色是否接受用户观点。

### 10.2 示例

| 用户表达 | 水上由岐的默认处理 |
|---|---|
| “这下坏了” | `allowed` |
| “绷不住了” | `allowed`，低频使用 |
| “草” | `observe_only` 或低频 `allowed`，由角色卡决定 |
| 强烈辱骂 | `rejected` 或 `observe_only` |
| 口吃、重复字模仿 | `rejected` |
| 与角色核心冲突的过度卖萌 | `observe_only` |
| 用户明确解释的私有内部梗 | 可进入 `interaction_rule`，但不等同于普通词语特征 |

### 10.3 与 Persona Loop 的边界

普通词语和句式不进入 `PERSONA_KINDS`，不生成 `user_framework` 或 `character_belief`。

只有用户明确解释表达含义、并形成双方可追溯的交互规则时，才允许转换为现有 Persona/Memory 候选，例如：

```text
用户：我说“堂堂起床”就是认真开始一天，不是普通的起床。
```

此时可以候选为：

```text
interaction_rule / user_framework
```

仍必须经过现有证据、主体、版本和用户确认规则。

## 11. 激活等级与频率控制

### 11.1 Observe

条件：第一次或第二次出现。

行为：不注入或只保留内部观察，不主动使用。

### 11.2 Mention

条件：出现达到候选门槛，但稳定性不足以自然复用。

行为：在确有关系意义时偶尔提及用户的表达习惯，不应每轮询问“你是不是喜欢这个词”。

### 11.3 Echo

条件：`confirmed`、角色适配为 `allowed`、当前作用域匹配。

行为：低频提示主 LLM 可以自然参考，不做字符串硬插。

### 11.4 Natural

第一阶段不启用。未来即使启用，也必须满足更高门槛：

```text
出现至少 10 次
跨至少 3 个自然日
跨至少 3 个场景
近期无负向反馈
角色适配稳定
近 20 轮没有过度使用
```

“自然内化”仍然只是提示强度变化，不代表程序强制把词插入回复。

### 11.5 频率硬限制

默认建议：

```text
单轮最多激活 1 个表达特征
同一特征至少冷却 5 轮
同一特征每天最多使用 3 次
所有表达特征合计至少间隔 3 轮
confirmed 特征总数最多 24 条
```

当限制达到时，直接不注入表达特征，不生成“我现在不能用这个”的用户可见提示。

## 12. 激活排序

激活器只负责从已通过硬门槛的特征中选择最多一个候选，输出低权重 prompt block。建议排序信号：

```text
0.30 * confidence
+ 0.20 * context_match
+ 0.15 * scope_match
+ 0.15 * recency
+ 0.10 * relationship_fit
+ 0.10 * role_compatibility
- 0.30 * recent_overuse
- 0.40 * negative_feedback
```

该分数只能排序，不能绕过硬门槛。

硬门槛顺序：

```text
status == confirmed
→ role_compatibility == allowed
→ 当前用户没有明确禁止
→ 当前场景允许表达特征
→ 当前通道允许该类型
→ 冷却和每日上限通过
→ 取最高分一个
```

以下场景默认不主动激活，或仅允许 `observe_only`：

- 严肃事实核对；
- 技术错误排查；
- 用户明确边界或冲突；
- 危机、强烈悲伤或需要认真接住情绪的输入；
- 用户要求简短、准确或正式回答；
- 表达特征与当前话题无关。

## 13. Prompt 注入协议

表达特征以短摘要注入 `StyleBrief` 或 `ResponsePlan`，不把特征库原始对象整体塞进 prompt。

词语示例：

```text
【表达适配·低权重】
用户有一个稳定表达习惯：常用“绷不住了”表示无奈或好笑。
当前语境适用度：中。
如果自然，可以参考一次；不要逐字复述用户原句，不要解释自己正在学习用户。
角色核心、事实正确和用户本轮要求优先。
```

句式示例：

```text
【表达适配·句式】
用户有时用“又……是吧？”表达轻度调侃。
只在关系和语境合适时参考，不要强行套用。
```

强制约束：

- 不注入 `feature_id`、内部状态、原始来源消息、confidence 数值或审计字段；
- 不注入完整样例句；
- 不要求模型解释“我正在模仿你”；
- 不要求模型每次使用；
- 不允许表达特征改变事实、立场、人格核心或安全边界；
- 仍然经过统一 Reply 解析，不能因为表达特征而放宽 JSON、思考过程或内部 prompt 清理。

## 14. 通道规则

### 14.1 IM

可以参考：

- 低风险词语；
- 低频句式；
- 用户的换行、括号和短句节奏，但这些优先由 `UserStyleProfile` 处理。

不允许：

- 直接复制用户完整句子；
- 把内部学习说明发送给用户；
- 让表达特征绕过 `render_im()`。

### 14.2 TTS

可以参考：

- 句长；
- 停顿和节奏；
- 低风险词语（角色和语言允许时）。

默认不注入：

- emoji；
- 纯文字标点特征；
- 只适用于 IM 的括号、颜文字和视觉格式；
- 用户文本中的 URL、内部 prompt 或审计信息。

TTS 仍遵守现有双语协议：`ja` 只送语音，`zh` 作为显示文本，表达特征不能改变该通道契约。

## 15. 反馈、修正和撤回

### 15.1 正向信号

可作为弱反馈：

- 用户继续自然使用该表达；
- 用户明确说“你学得还挺像”；
- 用户没有纠正且继续相关话题；
- 用户对回复给出明确正向反馈。

弱反馈不能直接把候选晋升为 confirmed。

### 15.2 负向信号

包括：

```text
别学我说话
你这样说很怪
不要用这个词
你理解错了
这不是这个意思
```

处理：

```text
confirmed -> observe_only
candidate -> rejected 或冷却
use_count 清零
冷却至少 7 天
```

### 15.3 用户明确撤回

用户明确要求删除或停止学习时：

1. 立即从激活器移除；
2. 标记 `user_rejected=true`；
3. 不再采集同一特征，除非用户明确重新允许；
4. 删除来源关联和可恢复原文；
5. 只保留无原文的撤回审计信息；
6. 重启后不能恢复激活状态。

## 16. 衰减、过期与容量

默认设计参数：

```text
候选观察窗口：14 天
候选 14 天未再次出现：expired
confirmed 30 天未出现：降为 observe_only
confirmed 90 天无使用且无用户确认：允许彻底删除
```

用户明确确认的表达含义如果已进入 `interaction_rule` 或其他长期记忆层，按现有 MemoryStore 版本链管理，不由普通表达特征过期逻辑静默删除。

所有特征均受容量上限约束。超过上限时：

1. 优先淘汰低置信度、低使用、长期未出现的特征；
2. 不淘汰用户明确确认且仍有效的交互规则；
3. 不把淘汰当作用户可见事件；
4. 删除仍必须可审计和可重试。

## 17. 失败降级

| 失败 | 行为 |
|---|---|
| 候选解析失败 | 保留普通对话，不学习本轮 |
| 敏感检查异常 | fail-closed，不激活 |
| 角色适配无法判断 | `observe_only` |
| style 状态文件损坏 | 使用角色默认风格，不阻断对话 |
| 激活状态过期 | 清空本轮表达适配，不发送错误文案 |
| LLM 标注超时 | 使用规则候选或跳过本轮 |
| 负反馈识别不确定 | 不自动降级，等待更多证据 |
| 表达特征和用户本轮要求冲突 | 用户本轮要求优先 |

任何内部异常都不能把 JSON、候选对象、思考过程、provider 错误或审计字段送入 IM/TTS。

## 19. 未来实现后的行为验收标准

本节是未来重新启动该功能后的验收门槛，当前不执行，也不代表现有远程 API 链路已经具备这些能力。

### 19.1 离线测试

必须覆盖：

1. 单次出现不激活；
2. 三次出现进入 candidate；
3. 跨天/跨场景后才允许 confirmed；
4. 主题专名不进入表达特征；
5. 敏感词、凭据和身份信息不进入；
6. 用户明确禁止后不再激活；
7. 角色不适配时为 `observe_only`；
8. 单轮最多一个特征；
9. 同一特征冷却和每日上限生效；
10. TTS 不注入 emoji/纯文字标点特征；
11. 用户本轮明确风格要求覆盖统计和表达特征；
12. Reply 不出现 feature_id、confidence、内部标签或原始候选；
13. 角色切换后不泄漏不适配特征；
14. 删除后重启仍不恢复；
15. 原始完整句子未进入表达特征持久化；
16. 只从 user_text 学习，assistant/system/tool 内容不会污染候选。

### 19.2 生产链验收

若未来采用运行时表达特征方案，至少使用对应模型连续 20 轮对话，检查：

```text
user_text
→ feature observation
→ prompt 注入
→ LLM 返回
→ Reply 解析
→ Memory/Style 状态保存
→ IM/TTS 渲染
→ 用户可见输出
```

验收指标：

```text
内部特征对象泄漏：0
用户完整原句复读：0
单轮激活特征：<= 1
明确撤回后的再次激活：0
敏感/主题实体误学习：0
角色核心冲突：0
Reply 解析错误：0
```

### 19.3 人工体验验收

用户应能感知到：

- AI 偶尔听懂或提到用户的表达习惯；
- AI 没有每轮刻意学舌；
- AI 仍然像角色自己；
- 用户拒绝后它会停止；
- 复杂、严肃或技术场景不会强行玩梗；
- 不会因为学习表达而泄漏用户原文或内部 prompt。

## 20. 未来动工时的默认决策清单

以下只作为未来重新动工时的默认方案，若用户后续重新启动本功能并修改，以新的明确决定为准；当前不代表任何功能已启用：

1. MVP 学习对象：低风险词语和少量句式。

10. 兼容性：保留 `LanguageMirror` facade，不一次性改动所有调用方。

## 21. 暂缓原因与未来本地模型路线

### 21.1 当前明确暂缓

当前 Veranima 使用远程 OpenAI 兼容 API。表达特征学习暂不实现，原因是：

- 当前优先保证回复协议、思考过程清理、记忆边界和双端生产链稳定；
- 远程 API 不适合把用户表达数据用于在线权重更新；
- 用户表达学习涉及授权、隐私、原文泄漏、角色漂移和撤回删除，不能先做一个低可靠版本；
- 现有 `StyleProfile` 的统计能力不应被误称为“表达基因迁移”已实现；
- 当前不新增采集开关、数据库字段、训练脚本或运行时 prompt 激活逻辑。

### 21.2 未来切换本地模型后的可选路线

如果后续将远程 API 替换为本地模型，可以重新评估使用**离线模型微调或 LoRA/adapter**实现表达风格迁移。该路线不是当前承诺，也不等同于一定采用 LoRA。

重新评估至少需要满足：

1. 使用者明确授权的本地语料，且完成敏感信息清理、去重和来源登记；
2. 训练集、验证集、保留集和原文泄漏评测集分离；
3. 先建立 Profile-only / prompt-only 基线，证明统计方案确实不足；
4. 微调产物独立于角色卡、事实记忆和关系状态，可单独启用、停用和回滚；
5. 记录基座模型哈希、数据版本、训练参数和 adapter 版本；
6. 验证角色核心一致性、事实保持率、原文 n-gram 泄漏、跨场景泛化和用户撤回后的删除边界；
7. 本地模型的上下文、显存、推理延迟和 TTS/多模态能力经过真实环境验收；
8. 即使微调启用，Reply 解析、内部思考清理、IM/TTS 分通道和现实行动边界仍由运行时程序控制。

未来可选路线应当是：

```text
授权本地语料
  -> 脱敏/去重/分集
  -> Profile-only 基线
  -> 离线 adapter/LoRA 实验
  -> 泄漏/角色/事实评测
  -> 独立版本启用或回滚
```

不能因为切换到本地模型，就把未经授权的聊天历史直接用于训练，也不能用模型微调替代表达特征的删除、撤回和安全边界。
